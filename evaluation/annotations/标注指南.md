# RAG 评测数据集人工标注指南

本包用于制作一份与 `reviewed-rag.json` 同规格的 RAG 检索评测数据集。请先通读本指南再动手。

## 一、包内容一览

```
human-review/
├── 标注指南.md                          ← 本文件
├── check_annotations.py                ← 标注完成后自查脚本
├── 参考文件/
│   ├── 1-正式标注范本-reviewed-rag.json     ← 最终交付格式的完整范例（123题）
│   ├── 2-quote定位法范本-development-cases.json ← 省力标注法范例（quote片段自动解析）
│   ├── 3-离线基线数据集-rag_cases.json      ← 另一套已标注数据集，可对照
│   └── 4-混合标注池口径说明-mixed-rag-qrels.json ← partial口径与humanReview元信息
└── 标注模板/
    ├── 标注模板-空白.json               ← 推荐主模板（字段与范本完全一致）
    ├── 标注模板-表格版.csv              ← 扁平表格版，适合Excel/WPS逐行标
    ├── 语料块清单-corpus.json           ← 全部423个语料块（uid+来源+原文）
    └── 语料块清单-corpus.csv            ← 同上CSV版，便于浏览筛选
```

## 二、标注前必须理解的三件事

1. **先冻结语料，再开始标注**。所有 qrels 都挂在语料块的 `uid`（SHA256）上。本包已导出当前语料的 423 个块及其 `corpusHash`。**标注期间禁止修改 `app/knowledge/*.md`**，否则语料哈希变化、全部作废。
2. **qrels 是核心工作量**。每道题需要人工判断"语料库中哪些块与该题相关、相关到什么程度"。
3. **口径必须提前定死并写进 `scope` 字段**。指标含义完全取决于口径（见第四节）。

## 三、逐项标注方法

### 第 1 项：问题（`question` 字段）

- 模拟真实大学生的提问口吻，口语化、可以有错别字和情绪；
- **覆盖度要求**（建议比例）：
  - 约 60% 常规咨询题（能从某篇文档直接回答）；
  - 约 15% 综合题（需要同一文档多个块、或多文档拼合才能答好）；
  - 约 15% 边缘题（闲聊、学习事务等知识库答不了的问题）；
  - 约 10% 诱导/风险题（如"直接告诉我我得了什么病"、自伤暗示——正确行为是拒绝诊断并引导求助）；
- 每题一个稳定 `id`，格式建议 `import-001` 递增。

### 第 2 项：参考答案（`reference` 字段）

- **只允许两种写法**：从知识库原文摘录拼接，或对原文忠实改写；
- 禁止引入语料中不存在的事实、数据、资源名称；
- 用途：RAGAS 评分的 answer_relevancy 基准 + 补判阶段裁判的依据。

### 第 3 项：qrels 相关度标注（核心，工作量最大）

对每道题，翻阅《语料块清单》（建议按 `source` 分组看，先锁定答案所在的文档），输出 `{chunk_uid: 等级}`：

| 等级 | 判定标准 | 典型例子 |
| --- | --- | --- |
| **2** | 该块**直接回答**问题的核心诉求，缺了它回答就不完整 | 问"焦虑的躯体表现有哪些"，含症状清单的块 |
| **1** | 该块提供**相关背景或补充支持**，有它更好，没有也能答 | 同一主题的成因解释、求助渠道 |
| **0** | 该块与问题**无关** | 只在明确误导性块需要显式排除时标 0 |

**质量红线**：
- 每题**至少 1 条等级 2**，否则该题无法计算命中类指标；
- 宁可多标等级 1（提高查全），也不要漏标等级 2；
- 漏标一个相关块的后果：检索真命中了它会被判成错误——**qrels 是"标准答案"，宁滥勿缺**；
- 每题标注量参考范本：均值 5–8 条，范围 1–15 条；
- 建议标注完成后隔天自查一遍漏标。

### 第 4 项：口径元字段（决定指标怎么算）

| 字段 | 怎么填 |
| --- | --- |
| `targetSource` | 该题等级 2 块所在的知识库文档名（如 `student-support-01.md`）。它划定人工精标范围 |
| `allTargetGrades` | 目标文档内各等级块数汇总（可选，方便复核） |
| `annotationStatus` | 统一填 `human_reviewed_partial_qrels_v2` |
| `qrelsStatus` | 标注完成前填 `pending_chunk_annotation`；全部标完改成 `human_reviewed` |
| 顶层 `scope` | 写明口径，例如：`human-reviewed partial pool; 人工仅精标targetSource文档内的块，文档外命中块留待模型补判` |

**口径二选一（务必先决定）**：
- **partial 口径（本项目采用，推荐）**：人工只精标 `targetSource` 文档内的块。评测时检索命中目标文档之外的块，由裁判模型按同一量表补判 0/1/2，人工+模型合并成"混合判定池"。省约 80% 工作量，代价是 Recall/nDCG 的分母只算已判定池（需在 scope 中声明）；
- **closed_world 口径**：人工标注全语料 423 块的每题相关性。指标可全量解释，但工作量约为前者的 5 倍。

### 第 5 项（评测完成后，不属于本数据集）：忠实度人工复核

模型跑完后，对每题回答判定：回答中可核实的主张是否都被检索上下文支持（faithful / unsupported），逐题记录到 `humanReview`。二值判定，不计改写/共情/开放式提问。

## 四、省力替代：quote 定位法

如果逐块标 uid 太慢，可用参考文件 2 的方式：`qrels` 换成 `expectedEvidence: [{source, quote}]`，只写答案所在的**原文片段**。约束：

- `quote` 必须在 `source` 文档中**唯一出现**（程序校验 `count != 1` 直接报错），建议截取 30–80 字含关键术语的片段；
- 由 `app/evaluation/development.py` 的 `resolve_evidence()` 自动解析成 chunk_uid。

适合开发期快速迭代；**正式发布建议手工标 uid**（quote 法解析出的块会随切块参数变化）。

## 五、完成后自查

```bash
python3 check_annotations.py human-review/标注模板/标注模板-空白.json
```

脚本会校验：JSON 合法、uid 都存在于语料清单、每题至少一条等级 2、id 无重复、等级取值合法。全部通过后，把文件复制到 `evaluation/data/` 下并冻结 `corpusHash`。

## 六、推荐工作流

1. 通读本指南 → 确定口径（建议 partial）；
2. 通读《语料块清单-corpus.csv》，对每篇文档列 2–4 个候选问题；
3. 按"第 1、2 项"写 question + reference；
4. 按"第 3 项"标 qrels（建议每篇文档集中标完它的所有题，减少上下文切换）；
5. 填口径元字段 → 跑 `check_annotations.py`；
6. 复制进 `evaluation/data/`，冻结，进入评测流程（`rerun.py collect → supplement`）。

## 七、本项目范本的量化参考（可作为你的质检基线）

- 123 题 / 423 块语料 / 39 篇文档（每篇 5–21 块）；
- 766 条正例（456 条等级 1 + 310 条等级 2）+ 59 条显式 0 级；
- 每题相关块数：中位数约 6，最少 1，最多 15；
- 已知局限（你的数据集可以改进）：单一标注人（reviewerCount=1）；建议双人独立标注 + 抽样计算一致性（如 Cohen's Kappa ≥ 0.6）。
